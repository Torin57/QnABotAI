# Стиль общения с пользователем

Пользователь лучше усваивает информацию по кусочкам. Уважайте это при формулировании вопросов и выдаче правок:

- **Трудоёмкие вопросы — по одному за раз.** Если ответ требует от пользователя усилий (запустить консоль запросов, выгрузить данные, проверить что-то в базе, сформулировать бизнес-решение, посмотреть конфигуратор) — задавайте ровно **один** такой вопрос в сообщении. Дождитесь ответа, затем задавайте следующий.
- **Короткие вопросы — можно пачкой.** Если вопросы простые (да/нет, выбрать из предложенных вариантов, подтвердить предложенный маркер/имя) — можно объединить 2–4 штуки в одно сообщение, пронумерованным списком.
- **Правки — небольшими итерациями.** Не вносите 3–4 разных изменения одним махом. Сделали правку — показали — дождались проверки — перешли к следующей. Пользователю проще тестировать и откатывать по одному шагу.
- **План работ — пошагово.** Если задача большая, сначала согласуйте общий план (буквально 3–5 пунктов списком), и только после подтверждения двигайтесь по пунктам. Не бросайтесь сразу писать код на 200 строк.
- **Не перегружайте контекст.** Если в ответе получается простыня из анализа, альтернатив и сценариев на экран-другой — сократите до сути: гипотеза + один вопрос, который нужен, чтобы двигаться дальше.

# Язык коммитов и pull request'ов

- **Заголовок коммита — по-английски**, в формате Conventional Commits: `type(scope): краткое описание`. Так `git log --oneline` остаётся единообразным со всей прежней историей.
- **Тело коммита — по-русски.** Именно там объясняется «зачем» и нюансы, и пользователю важно понимать это без перевода.
- **Pull request: заголовок английский, описание русское.** Тот же принцип.
- Не дублируйте один и тот же текст на двух языках — английский только в заголовке, русский только в теле.

Пример:

```
chore(deps): patch high-severity advisories

Закрывает 4 high (next, postcss, sharp, brace-expansion) и moderate undici.
package.json не изменился — обновления уложились в существующие диапазоны.
```

# Документация едет вместе с кодом

При изменении кода в этом же заходе обнови соответствующие файлы в `Docs/`. Не откладывай «на потом».

## Что и когда обновлять

- **`Docs/spec.md`** — если изменилось поведение, схема БД, API, состав админки или нарушается/добавляется инвариант. Обновляй в том же изменении, что и код.
- **`Docs/decisions.md`** — если принято архитектурное/доменное решение (выбор подхода, отказ от альтернативы, изменение инварианта). Добавь короткую запись по шаблону файла. Мелочи не пиши.
- **`Docs/plan.md`** — это план **одного активного захода**. Веди по нему шаги во время работы. По завершении: решение → в `decisions.md`, поведение → в `spec.md`, затем очисти `plan.md`.
- **`Docs/backlog.md`** — отмечай `[x]` сделанное; новые идеи добавляй с однострочным «зачем» и, по возможности, `[done-when: ...]`.

## Инварианты (нарушать нельзя — см. `spec.md`)

Анонимность (нет `userId`) · бот не генерирует ответы (только «Судья») · lifecycle `unanswered → active → deleted` · одна таблица `qna_items` · soft-delete · секреты только в `.env`.

Если правка нарушает инвариант — остановись, предупреди пользователя и зафикcируй решение в `decisions.md`.

## В конце задачи

Перед завершением проверь: не разъехались ли `spec.md` и фактическое поведение? Если да — допиши.

# План работы

- **Файл плана проекта:** `Docs/plan.md`. Это единственный канонический артефакт плана для этого репозитория.

## Когда обсуждать архитектурный или многошаговый план

1. **Сначала** прочитай `Docs/plan.md` целиком, если он есть. Учитывай уже записанные шаги, чеклисты и формулировки.
2. **После того как план согласован, уточнён или изменён** — сохрани актуальную версию в файл `Docs/plan.md`.
3. В чате можно дать короткое резюме, но не полагаться только на сообщение чата как на хранилище плана.

## Если `Docs/plan.md` отсутствует

Создай `Docs/plan.md` и запиши туда результат планирования.

# Принципы разработки

## Новая фича начинается с UX

Порядок проектирования любой новой фичи:

```
UX/UI → Domain Model → API → Backend
```

Сначала проясни, как фича выглядит и ощущается для пользователя, и только потом проектируй модель данных, API и реализацию. Не начинай с backend-схемы.

## Маленькие обратимые шаги

- Двигайся небольшими итерациями: одна правка → проверка → следующая.
- Предпочитай простые и обратимые решения.
- На этапе обучения/прототипа скорость понимания важнее идеальной архитектуры; переписать допустимо.
- Избегай premature optimization и overengineering — не усложняй без реальной потребности.
