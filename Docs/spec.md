# Спецификация (SDD): Семантический FAQ-бот с админкой на Next.js

## 1. Описание проекта
Telegram-бот, который отвечает на вопросы студентов, используя базу знаний (FAQ). 
Бот НЕ генерирует ответы "из головы". Он использует векторную БД для предварительного поиска, а затем применяет легковесную LLM в роли "Судьи" для выбора единственно верного статичного ответа. 
Интерфейс преподавателя реализован в виде веб-приложения на Next.js. Весь проект реализован в едином стеке на TypeScript/Node.js.

## Инварианты (must-have, нарушать нельзя)

Жёсткие правила домена. Любая правка обязана их сохранять. Если правка их нарушает — это меняет суть продукта, и решение должно пройти через `decisions.md`.

1. **Анонимность.** Telegram `userId` (и любой идентификатор пользователя) НЕ сохраняется и НЕ отображается — ни в БД, ни в UI, ни в экспорте.
2. **Никаких галлюцинаций.** Бот не генерирует ответы. LLM работает только как «Судья»: выбирает готовый ответ из кандидатов Qdrant или возвращает `NULL`. Ответ всегда берётся из базы знаний.
3. **Единый lifecycle записи:** `unanswered | not_helpful | draft → active → deleted`. `unanswered` — бот не нашёл ответ; `not_helpful` — ответ был выдан, но ученик нажал «Это не помогло»; `draft` — пара извлечена ИИ из документа и ждёт одобрения преподавателя. Статуса `pending` нет.
4. **Одна таблица `qna_items`.** Неотвеченные вопросы — не отдельная сущность, а состояние `unanswered`. Отдельной таблицы `unanswered_queries` не существует.
5. **Soft-delete.** Удаление — это `status="deleted"`, данные физически не теряются.
6. **Секреты только в `.env`.** Никаких ключей в коде/репозитории.

## 2. Стек технологий (Fullstack TypeScript)
- **Telegram Бот:** Node.js, библиотека `grammY`.
- **Фронтенд и Бэкенд админки:** `Next.js` (App Router, React, TailwindCSS).
- **База данных:** `SQLite` + `Drizzle ORM` (логи и база FAQ-элементов).
- **Векторная БД:** Qdrant, запущенный локально через Docker Desktop (`docker-compose.yml`). Данные хранятся в папке `qdrant_storage/` (volume mount).
- **Эмбеддинги и LLM:** API Mistral (`mistral-embed` для векторизации; `mistral-small-latest` по умолчанию для извлечения пар из документов и для «Судьи» — модель/температура «Судьи» настраиваются в админке, см. §4 `app_settings` и §5 «Настройки»).
- **Парсинг документов:** `pdf-parse` (PDF), `mammoth` (DOCX), `exceljs` (Excel .xlsx); TXT и субтитры SRT/VTT разбираются своим кодом без внешних зависимостей (`src/lib/parser/extractText.ts`).
- **Окружение:** `dotenv` для ключей.

## 3. Архитектура и логика

### 3.1 Пайплайн загрузки базы знаний (два пути)

Преподаватель загружает материалы через веб-интерфейс. Путь обработки зависит от типа файла:

**Путь A — Excel (.xlsx):** Самый быстрый способ. Файл содержит готовые пары вопрос-ответ в колонках.
1. Преподаватель загружает `.xlsx` файл (колонки: `question`, `answer`).
2. Сервер читает строки напрямую через `exceljs` — LLM не нужна.
3. Пары сохраняются в `qna_items` со статусом `active` и сразу индексируются в Qdrant.

**Путь B — PDF / DOCX / TXT / SRT / VTT:** Для загрузки неструктурированных учебных материалов (конспекты, транскрипты уроков, субтитры).
1. Преподаватель загружает `.pdf`, `.docx`, `.txt`, `.srt` или `.vtt` файл.
2. Сервер извлекает текст: `pdf-parse` / `mammoth` для PDF/DOCX; TXT читается как есть; из SRT/VTT вырезаются заголовок `WEBVTT`, служебные блоки, номера реплик, таймкоды и теги разметки — остаётся связный текст (`subtitlesToPlainText`).
3. Текст документа сохраняется как материал для генерации ответов: запись в `documents` + фрагменты ~1000 символов в `doc_chunks` (для субтитров у фрагмента сохраняется секунда начала из таймкодов), затем фрагменты индексируются в коллекцию Qdrant `{QDRANT_COLLECTION}_docs`. Эмбеддинги считаются **пачками** (до 32 текстов / 32 000 символов на запрос к `mistral-embed`) — иначе транскрипт на 100+ фрагментов упирается в лимит Mistral 60 запросов в минуту. Все вызовы эмбеддингов в процессе (загрузка, переиндексация, поиск по вопросу из бота) идут через одну очередь с интервалом не быстрее 1 запроса в секунду; после 429 повтор через 5 / 15 / 45 с либо через время из заголовка `Retry-After`. Каждая пачка попадает в Qdrant сразу, поэтому обрыв на середине сохраняет уже проиндексированное. Повторная загрузка файла с тем же именем заменяет старую версию документа (см. §3.5).
4. Текст отправляется в `mistral-small-latest`: *"Извлеки все пары вопрос-ответ, верни JSON `{pairs:[{question,answer}]}`"*.
5. Пары сохраняются в `qna_items` со статусом `draft` (**без** индексации в Qdrant) и появляются во вкладке «Черновики» — бот их не видит, пока преподаватель не опубликует (по одной или массово).

**Сбой индексации не отменяет загрузку.** Фрагменты уже лежат в SQLite, поэтому ошибка индексации (например, недоступный Qdrant или лимит Mistral) только логируется — извлечение пар и создание черновиков продолжается. `POST /api/qna/upload` отвечает `{ imported, chunks: { total, indexed } }`; если `indexed < total`, админка показывает второй тост о неполном поиске по этой лекции. Индекс восстанавливается `npm run qdrant:reindex` (§7).

**Путь C — Ручной ввод:** Преподаватель добавляет одну пару вопрос-ответ вручную через форму на `/admin/qna` (`POST /api/qna`). Запись создаётся со статусом `active` и сразу индексируется в Qdrant. Используется для быстрой правки/дополнения базы без файла.

Доверенные пути (Excel, ручной ввод) попадают в базу сразу как `active`; LLM-извлечённые пары (путь B) проходят модерацию через `draft`. Статуса `pending` нет.

### 3.2 Обработка сообщения (Бот) — Гибридный поиск
0. **Rate limit:** не более **3 вопросов в минуту на чат** (скользящее окно). Счётчик по `chat_id` живёт только в памяти процесса (`src/lib/rate-limit.ts`) и в БД не пишется — инвариант анонимности соблюдён. При превышении бот один раз за эпизод блокировки отвечает «Слишком много вопросов подряд…», остальные сообщения в окне молча игнорируются; до Qdrant/Mistral запрос не доходит.
1. Пользователь пишет вопрос. Текст векторизуется через `mistral-embed`.
2. Выполняется поиск по Qdrant — извлекаются **Топ-3** самых похожих вопроса-ответа.
3. Топ-3 и вопрос пользователя отправляются в модель «Судьи» (по умолчанию `mistral-small-latest`, имя и температура — из `app_settings`): *"Выбери кандидата из базы знаний, который точно отвечает на вопрос. Верни только ID. Если не подходит ни один — верни 'NULL'"*.
4. Если LLM вернула ID: бот выдаёт заготовленный ответ из базы знаний и Inline-кнопку **«Это не помогло»** (callback с id записи в `bot_log`). По нажатию: вопрос пишется в `qna_items` как `not_helpful`, отвергнутый ответ сохраняется в `rejected_answer`, в `bot_log` добавляется событие с вердиктом `not_helpful` (снапшот того же ответа), клавиатура у ответа снимается, ученику — «Спасибо, передали вопрос преподавателю.» Повторный клик не создаёт дубликат.
5. Если LLM вернула `NULL`: бот отвечает "Не нашёл ответа" и выдаёт Inline-кнопку "Связаться с преподавателем".

### 3.3 Логирование вопросов для преподавателя
Вопросы, получившие `NULL`, записываются в **ту же таблицу** `qna_items` со статусом `unanswered` (поле `answer` пустое). Если ученик нажал «Это не помогло», создаётся запись `not_helpful`: новый исправленный `answer` пока пуст, а выданный ученику ответ хранится отдельно в `rejected_answer`. Telegram ID пользователя **не сохраняется** — бот анонимный. Оба статуса — начальные состояния жизненного цикла: `unanswered | not_helpful → active → deleted`.

### 3.4 Журнал обращений к боту (`bot_log`)
Независимо от исхода (найден ответ / `NULL` / ошибка обработки / «не помогло»), события фиксируются в отдельной анонимной таблице `bot_log` — это лог событий, а не редактируемая сущность (в отличие от `qna_items`). Пишется: вопрос пользователя, топ-3 кандидата из Qdrant со `score` (JSON, без их ответов — «Судья» ответы кандидатов не видит, см. `decisions.md`), вердикт (`answered` / `null` / `error` / `not_helpful`), снапшот выданного ответа (для `answered` и `not_helpful`), для `error` — текст ошибки (без stack trace), дата. При ошибке обработки (catch в `message:text`) запись делается best-effort: сбой записи лога не роняет обработчик. Просмотр — read-only таблица на `/admin/log` («Журнал»): `#`, Вопрос, Вердикт, Выданный ответ, Дата; кнопка «Подробнее» открывает модалку с разбором (см. §5 «Журнал»).

### 3.5 Генерация черновиков ответов по материалам (RAG, только в админке)
Для вопросов `unanswered` / `not_helpful` в админке есть кнопка **«Сгенерировать ответ»** (`POST /api/qna/[id]/generate`):
1. Вопрос векторизуется, из коллекции `{QDRANT_COLLECTION}_docs` берётся топ-4 фрагмента лекций.
2. `mistral-small-latest` (температура 0.2) собирает ответ **строго по фрагментам** и возвращает JSON `{answer, source}`; для `not_helpful` в промпт передаётся отвергнутый ответ как антипример. Если фрагменты не отвечают на вопрос — модель возвращает `null`, API отдаёт 404 («в материалах ответа не нашлось»).
3. К ответу добавляется отсылка к источнику: `Подробнее: <файл>, ~N-я минута` (минута — из таймкодов субтитров; для PDF/DOCX/TXT — только имя файла).
4. Черновик открывается в поле редактирования — преподаватель правит, сохраняет и публикует как обычно.

**Инвариант «бот не генерирует» не нарушается:** генерация доступна только преподавателю в админке; ученикам уходит только одобренный и опубликованный текст. Если материалы не загружены — API честно отвечает 404 с подсказкой загрузить транскрипты.

## 4. Схема базы данных (SQLite / Drizzle ORM)

### Таблица `qna_items` (единственная)
| Поле | Тип | Описание |
|---|---|---|
| `id` | integer PK | Автоинкремент |
| `question` | text NOT NULL | Вопрос |
| `answer` | text NULL | Новый/актуальный ответ (пуст для `unanswered` и нового `not_helpful`) |
| `source_document` | text NULL | Имя исходного файла (пусто для вопросов из бота) |
| `status` | text NOT NULL | `unanswered` / `not_helpful` / `draft` / `active` / `deleted` (default `unanswered`) |
| `rejected_answer` | text NULL | Снапшот ответа, который ученик отверг (для `not_helpful`) |
| `created_at` | integer | Timestamp создания |

Отдельной таблицы `unanswered_queries` больше нет — неотвеченные вопросы хранятся в `qna_items` со статусом `unanswered`.

### Таблицы `documents` и `doc_chunks` (учебные материалы для генерации)

Материалы, загруженные через «Загрузить документ» (путь B): источник для RAG-генерации черновиков ответов (см. §3.5). Повторная загрузка файла с тем же именем заменяет документ и его фрагменты целиком (в SQLite и Qdrant).

| Поле (`documents`) | Тип | Описание |
|---|---|---|
| `id` | integer PK | Автоинкремент |
| `file_name` | text NOT NULL | Имя загруженного файла (оно же «название урока» в отсылке) |
| `created_at` | integer | Timestamp загрузки |

| Поле (`doc_chunks`) | Тип | Описание |
|---|---|---|
| `id` | integer PK | Автоинкремент (он же id точки в Qdrant `_docs`) |
| `document_id` | integer NOT NULL FK | Ссылка на `documents.id`, `ON DELETE CASCADE` |
| `idx` | integer NOT NULL | Порядок фрагмента внутри документа |
| `text` | text NOT NULL | Текст фрагмента (~1000 символов) |
| `start_seconds` | integer NULL | Секунда начала фрагмента в видео (только для SRT/VTT) |

### Таблица `bot_log` (журнал обращений к боту)
| Поле | Тип | Описание |
|---|---|---|
| `id` | integer PK | Автоинкремент |
| `question` | text NOT NULL | Вопрос пользователя |
| `candidates` | json NULL | Топ-3 кандидата из Qdrant: `[{id, question, score}]` (без ответов кандидатов) |
| `verdict` | text NOT NULL | `answered` / `null` — вердикт «Судьи»; `error` — сбой; `not_helpful` — ученик нажал «Это не помогло» |
| `answer` | text NULL | Снапшот выданного ответа (пусто при `verdict="null"` и `"error"`; при `not_helpful` — тот же отвергнутый ответ) |
| `error` | text NULL | Текст ошибки обработки (только при `verdict="error"`, без stack trace, до 500 символов) |
| `created_at` | integer | Timestamp обращения |

Анонимная (без `userId`), не связана с `qna_items` внешним ключом — это независимый поток событий.

### Таблица `app_settings` (настройки приложения)
Одна строка (`id = 1`) с параметрами, которые админ меняет из UI без правки `.env`.

| Поле | Тип | Описание |
|---|---|---|
| `id` | integer PK | Всегда `1` |
| `judge_model` | text NOT NULL | Имя модели Mistral для «Судьи» (дефолт `mistral-small-latest`) |
| `judge_temperature` | real NOT NULL | Температура «Судьи», 0–1.5 (лимит Mistral API; дефолт `0`) |
| `judge_prompt` | text NULL | Системный промпт «Судьи»; пусто/NULL → дефолт из кода |
| `teacher_contact_url` | text NULL | Ссылка кнопки «Связаться с преподавателем»; пусто/NULL → `TEACHER_CONTACT_URL` из `.env` |
| `tg_bot_token` | text NULL | Токен Telegram-бота; пусто/NULL → `TG_BOT_TOKEN` из `.env`. В API наружу только маска |
| `updated_at` | integer | Timestamp последнего сохранения |

Если строки ещё нет — бот и API используют дефолты в коде / `.env`. `MISTRAL_API_KEY` в эту таблицу **не** кладётся (только `.env`). Токен бота в БД — осознанное исключение для смены из админки (см. `decisions.md`); полный токен в UI не показывается.

## 5. Веб-интерфейс администратора (подробно)

Корень сайта (`/`) сразу перенаправляет на `/admin/qna` (далее — авторизация, см. §5.0).

### 5.0 Авторизация (`/admin/login`)

Доступ ко всем страницам `/admin/*` и API (`/api/qna/*`, `/api/log/*`, `/api/settings/*`) закрыт паролем (единственный админ, без логина — пилот на одного преподавателя).

- **Вход:** форма с одним полем «Пароль» на `/admin/login` → `POST /api/auth/login`. Пароль сверяется с bcrypt-хешем из `.env` (`ADMIN_PASSWORD_HASH_BASE64`, хеш закодирован в base64 — иначе `$` внутри bcrypt-хеша ломается переменной-экспансией Next.js при загрузке `.env`).
- **Сессия:** при успехе выставляется подписанный `httpOnly` cookie (`admin_session`), подпись — HMAC-SHA256 на `SESSION_SECRET` из `.env`. Срок жизни — 1 год (сессия сохраняется между визитами, повторный ввод пароля не требуется, пока cookie не очищена или не вызван выход).
- **Защита:** `src/proxy.ts` (Next.js proxy/middleware) проверяет cookie на каждом запросе к `/admin/*` (кроме `/admin/login`) и к `/api/qna/*`, `/api/log/*`, `/api/settings/*`. Без валидной сессии — редирект на `/admin/login` (страницы) или `401` (API).
- **Защита от перебора пароля:** 5 неудачных попыток входа с одного IP → блокировка на 15 минут, `POST /api/auth/login` отвечает `429` («Слишком много неудачных попыток…»). Успешный вход сбрасывает счётчик. Счётчик in-memory (`src/lib/rate-limit.ts`), в БД не пишется; IP берётся из `x-forwarded-for`.
- **Выход:** кнопка «Выйти» в шапке админки (`AdminNav`) → `POST /api/auth/logout`, cookie удаляется.
- **Настройка пароля:** `npm run admin:hash-password -- "пароль"` печатает base64-строку для `ADMIN_PASSWORD_HASH_BASE64`.

Обратная связь по действиям (успех/ошибка) выводится через toast-уведомления (`ToastProvider`/`useToast`, `src/components/Toast.tsx`), а не через `alert()`. Провайдер смонтирован в layout админки, доступен на всех страницах `/admin/*`.

### Шапка админки (`AdminNav`)
Навигация: «База знаний» / «Журнал». Справа — **«Настройки»** (не отдельная вкладка) и «Выйти».

**Модалка «Настройки»:** разделы **Судья** (модель, температура 0–1.5, системный промпт до 8000 символов; подсказка поясняет, что настройка модели действует только для «Судьи» и пока поддерживает только Mistral), **Контакт преподавателя** (ссылка для Inline-кнопки «Связаться с преподавателем», `http(s)://`, до 500 символов) и **Telegram-бот** (текущий `@username`; маска токена показывается только как fallback, если имя бота определить не удалось; поле «Новый токен» — пустое = не менять; «Сбросить к умолчанию» помечает возврат к `TG_BOT_TOKEN` из `.env`). Внизу слева — **«Сбросить к умолчанию»**, справа — «Отмена» / «Сохранить». API: `GET`/`PATCH /api/settings/judge`, `GET`/`PATCH /api/settings/contact`, `GET`/`PATCH /api/settings/bot`. Перед сохранением нового токена — проверка через Telegram `getMe`; при успехе токен пишется в `app_settings` и polling бота перезапускается без рестарта процесса. Полный токен в GET не отдаётся.
Единый список всех записей `qna_items`. Над списком — фильтр по статусу: **Все / Неотвеченные / Не помогло / Черновики / Активные / Удалённые** (`GET /api/qna?status=...`, `all` показывает всё, без параметра — скрываются `deleted`).

**Панель действий (вверху):**
- Кнопка «Добавить пару» — открывает модальную форму с полями `Вопрос` / `Ответ`. Оба поля обязательны. По сохранению создаётся запись со статусом `active` и сразу индексируется в Qdrant (`POST /api/qna`).
- Кнопка «Загрузить Excel» — открывает file picker, принимает `.xlsx`. Пары читаются из колонок `question` / `answer`, сохраняются как `active`.
- Кнопка «Загрузить документ» — принимает `.pdf` / `.docx` / `.txt` / `.srt` / `.vtt`. Запускает LLM-экстракцию пар вопрос-ответ; результат — черновики (см. §3.1, путь B).
- Кнопка «Экспорт в Excel» — скачивает все `active` QnA-пары в `.xlsx` файл.
- Под панелью — подсказка по форматам: что кладут в Excel (колонки `question`/`answer`) и что подходит для «Загрузить документ» (материалы в свободной форме, включая транскрипты и субтитры; ИИ сам извлечёт пары).

**Таблица QnA-пар:**
- Колонки: чекбокс, `#`, `Вопрос`, `Ответ`, `Статус`, `Дата`, `Действия`. **Без колонки «Пользователь»** — бот анонимный. Колонка «Источник» (имя файла-источника) скрыта из UI намеренно (см. `decisions.md`), но поле `source_document` в БД сохраняется.
- Действия на строке зависят от статуса:
  - **Сгенерировать ответ** (для `unanswered` и `not_helpful`) — RAG-черновик по загруженным материалам (см. §3.5); результат открывается в режиме редактирования.
  - **Опубликовать** (для `unanswered`, `not_helpful` и `draft`) — статус → `active`, публикация в Qdrant. Требует непустой `answer`; попытка опубликовать запись без ответа отклоняется с ошибкой (`POST /api/qna/[id]/publish` → 400).
  - **Изменить** — inline-форма для правки `question` и `answer`. У `not_helpful` над полем нового ответа показывается снапшот «Ответ, который не помог». Если статус `active`, обновляет вектор в Qdrant.
  - **Удалить** — статус → `deleted` (soft-delete), удаление из Qdrant (если был `active`).
  - Для `deleted`-записей чекбокс скрыт; вместо остальных действий — **Восстановить** (`POST /api/qna/[id]/restore`): статус → `active`, если есть непустой `answer` (с повторной индексацией в Qdrant); без ответа → `not_helpful`, если сохранён `rejected_answer`, иначе → `unanswered`.

**Сортировка:** заголовки колонок «Вопрос», «Ответ», «Дата» кликабельны — переключают сортировку (по возрастанию/убыванию, стрелка показывает направление). Сортировка клиентская, по уже загруженному (отфильтрованному) списку; по умолчанию — по дате создания, новые сверху.

**Bulk actions:** чекбокс в шапке таблицы выделяет/снимает все видимые (не `deleted`) записи; чекбоксы в строках — по одной. При выборе хотя бы одной записи появляется панель с количеством выбранного и кнопками **«Опубликовать выбранное»** (`POST /api/qna/bulk-publish` с `{ ids: number[] }` — записи с непустым `answer` и статусом не `active`/`deleted` переходят в `active` + индексируются в Qdrant; записи без ответа пропускаются, их число возвращается в ответе) и **«Удалить выбранное»** (`POST /api/qna/bulk-delete` с `{ ids: number[] }`, массовый soft-delete (`status → deleted`) + удаление из Qdrant для тех, что были `active`). Выделение сбрасывается при обновлении списка (смена фильтра, любое действие).

### Страница «Журнал» (`/admin/log`)
Read-only список последних 200 обращений к боту (`GET /api/log`), без фильтров — это поток событий для чтения, не редактируемая сущность. Колонки: `#`, Вопрос, Вердикт (Отвечен / Не найден / Ошибка / Не помогло), Выданный ответ (для вердикта «Ошибка» — текст ошибки красным), Дата, кнопка **«Подробнее»**.

**Модалка «Подробнее»:** вопрос, вердикт, выданный ответ (или текст ошибки), дата, блок **«Похожие вопросы из базы знаний»** — топ-3 из `bot_log.candidates` (вопрос + `score`) с актуальным ответом из `qna_items` (подтягивается в `GET /api/log` по id; в самом логе ответы кандидатов не хранятся — «Судья» их не видит). При вердикте «Отвечен» или «Не помогло» кандидат, чей ответ совпадает со снапшотом выданного, подсвечивается (светло-зелёный, метка «выбран»). Если похожих нет — пояснение в модалке. Навигация и кнопка «Настройки» — в шапке (`AdminNav`).

## 7. Требования к безопасности

Чек-лист угроз/митигаций, **trust boundaries** и шпаргалка реагирования на инциденты — в `Docs/threat-model.md` (лёгкая модель под масштаб пилота).

### 7.1 Разделение секретов по окружениям

Секреты хранятся только в gitignored-файлах. В репозитории — только шаблоны `*.example`.

| Окружение | Файл с секретами | Шаблон | Запуск |
|---|---|---|---|
| development | `.env.development.local` | `.env.development.example` | `npm run dev:server` |
| staging | `.env.staging.local` | `.env.staging.example` | `APP_ENV=staging NODE_ENV=production npm start` |
| production | `.env.production.local` | `.env.production.example` | `npm start` |

**Порядок загрузки** (совпадает с Next.js + staging): `.env` → `.env.local` → `.env.{APP_ENV}` → `.env.{APP_ENV}.local`. Более поздний файл перекрывает более ранний. Переменная `APP_ENV` (`development` \| `staging` \| `production`) определяет, какой набор секретов подхватить; `NODE_ENV` — режим рантайма Next.js.

**Telegram-бот:** на каждое окружение — **отдельный** бот и `TG_BOT_TOKEN` (через [@BotFather](https://t.me/BotFather)). Dev/staging не должны использовать prod-токен.

**Обязательные переменные:** `TG_BOT_TOKEN`, `MISTRAL_API_KEY`, `ADMIN_PASSWORD_HASH_BASE64`, `SESSION_SECRET`, `TEACHER_CONTACT_URL`, **`DATABASE_PATH`**, **`QDRANT_COLLECTION`** (имя коллекции Qdrant, например `qna_dev` / `qna_prod`; коллекция материалов называется автоматически `{QDRANT_COLLECTION}_docs` и отдельной переменной не требует). При старте `preload-env.ts` проверяют их наличие (`src/lib/load-env.ts`). В логах старта: `[server] database: …`, `[server] qdrant collection: …`.

**Защита от перепутывания окружений:** dev и prod живут на одной машине с общим Qdrant, поэтому `validateEnv()` дополнительно сверяет имена с `APP_ENV`: `QDRANT_COLLECTION` обязана оканчиваться на `_dev` / `_prod` / `_staging`, а имя файла в `DATABASE_PATH` — содержать `dev` / `prod` / `staging` соответственно. Несовпадение — ошибка при старте (защита от опечатки в `.env`, из-за которой dev-данные молча ушли бы в прод).

**`TG_BOT_TOKEN`:** fallback-токен бота при старте и после сброса в админке. Преподаватель может переопределить токен в модалке «Настройки» (`app_settings.tg_bot_token`); переменная в `.env` по-прежнему обязательна (bootstrap). На каждое окружение — свой бот/токен.

**`TEACHER_CONTACT_URL`:** fallback-ссылка (например, `https://t.me/username`) для Inline-кнопки «Связаться с преподавателем» (см. §3.2, п.5), если в `app_settings.teacher_contact_url` ещё ничего не задано. Преподаватель может переопределить ссылку в модалке «Настройки». Значение в `.env` своё на каждое окружение.

**Загрузка до импортов:** `tsx --import ./src/lib/preload-env.ts` в npm-скриптах — иначе клиент Mistral инициализируется до чтения `.env`.

**Миграция с одного `.env`:** скопировать секреты в `.env.development.local`; на prod-сервере создать `.env.production.local` с новым ботом и своими `SESSION_SECRET` / паролем админки.

**Раздельные рабочие папки на одном сервере:** прод — клон репозитория на ветке `main`, из которого работает systemd-сервис `qnabotai` (код туда попадает только через деплой, полный порядок — §7.4); дев — отдельный клон (`~/workspace/QnABotAI-dev`) со своими `.env.development.local` (включая `PORT=3001`) и `data/logs-dev.db`. Запускать `next dev` из прод-папки нельзя — он перезапишет прод-сборку в `.next/`.

### 7.2 Прочее
- Секреты только в gitignored `.env.*.local` (см. §7.1), не в репозитории.
- Ограничить размер загружаемого файла на сервере (не более 10 МБ).
- Разрешать только типы: `application/pdf`, `application/vnd.openxmlformats-officedocument.wordprocessingml.document`, `application/vnd.openxmlformats-officedocument.spreadsheetml.sheet`, `text/plain` (.txt), `application/x-subrip` (.srt), `text/vtt` (.vtt). Для текстовых типов расширение приоритетнее MIME из браузера (браузеры отдают `.srt` как `text/plain` или пустой тип).
- **Валидация содержимого:** перед парсингом PDF проверяется сигнатура `%PDF`, docx/xlsx — ZIP-сигнатура `PK\x03\x04`; текстовые файлы (.txt/.srt/.vtt) обязаны быть валидным UTF-8 без NUL-байтов, `.vtt` дополнительно — начинаться с `WEBVTT`. Несовпадение → `400` («Содержимое файла не соответствует его типу»).
- **Лимиты импорта** (`src/lib/parser/index.ts`): не более **500 пар** за одну загрузку (превышение → `400` с понятным текстом); вопрос обрезается до **1000** символов, ответ — до **8000** (обрезаем, а не отклоняем, чтобы не терять всю загрузку из-за одной длинной строки). Действует для обоих путей (Excel и LLM).
- Файлы `.env`, `data/`, `qdrant_storage/`, `backups/`, `node_modules/`, `.next/` в `.gitignore`.
- **Cursor / AI при разработке:** `.cursorignore` в корне (секреты, БД, бэкапы, `qdrant_storage/` не индексируются); Privacy Mode в Cursor — см. `decisions.md` 2026-07-05.
- Доступ к админке (`/admin/*`) и её API защищён паролем — см. раздел 5.0.

### 7.3 Бэкапы и восстановление

**Что является источником правды:** SQLite-файл по `DATABASE_PATH` из активного окружения (`qna_items` + `bot_log`). Dev и prod на одном VPS используют **разные файлы** (например `data/logs-dev.db` и `data/logs-prod.db`). Qdrant — производный индекс, восстанавливается из SQLite. Секреты (`.env.*.local`) скриптом не бэкапятся.

**Бэкап (автоматический, только production):**
- `scripts/backup.sh` читает `DATABASE_PATH` из `.env.production.local`, горячий бэкап через `sqlite3 ".backup"` → `backups/<имя-базы>-<дата>.db.gz` + `.sha256`; ротация 7 шт.
- Cron: ежедневно в 03:00 UTC, вывод в `backups/backup.log`.

**Восстановление (полный порядок, production):**
1. Остановить бот/сервер.
2. `gunzip -c backups/logs-prod-<дата>.db.gz > data/logs-prod.db` (путь = `DATABASE_PATH` из `.env.production.local`).
3. `sqlite3 data/logs-prod.db "pragma integrity_check;"` → `ok`.
4. Qdrant up, `APP_ENV=production npm run qdrant:reindex`.
5. Запуск и smoke-тест бота/админки.

`npm run qdrant:reindex` (`scripts/reindex.ts`) применим и отдельно — при потере/порче `qdrant_storage/` без потери SQLite, или при рассинхроне индекса с базой. Восстанавливает обе коллекции: пары вопрос-ответ и фрагменты материалов (`{QDRANT_COLLECTION}_docs`).

### 7.4 Деплой на production

**Ветки.** Работа идёт в `dev`, прод живёт на `main`. Код попадает в `main` только через PR `dev → main` (merge-коммит, не squash — история `main` остаётся сопоставимой с `dev`). Прод-папка ветку никогда не меняет.

**Изоляция папок (настроено 2026-08-06).** Прод-клон физически не знает о `dev`: локальная ветка удалена, `remote.origin.fetch` сужен до `+refs/heads/main:refs/remotes/origin/main`, ссылка `origin/dev` вычищена — `git checkout dev` падает с `pathspec did not match`. Вторым рубежом стоит хук `.git/hooks/post-checkout` (источник — `scripts/prod-post-checkout.sh`, ставится при деплое): предупреждает при уходе с `main`, в том числе в detached HEAD. В dev-клоне, наоборот, удалена протухшая локальная `main`, но `origin/main` виден — сравниваться с релизом можно.

**Как деплоить:** `scripts/deploy.sh` в прод-папке — он выполняет весь порядок ниже, проверяя перед этим, что запущен именно в прод-клоне (`.env.production.local` на месте), что ветка `main` и что рабочая копия чистая. Флаг `-y` пропускает подтверждение. При обрыве после остановки сервиса скрипт печатает, как поднять или откатить.

**Порядок (production, `~/workspace/QnABotAI`):**
1. `sudo systemctl stop qnabotai` — **до** `git pull`. Иначе между `pull` и миграциями на диске лежит новый код при старой схеме, и автоперезапуск юнита поднимет его на неготовой базе.
2. Бэкап БД: `scripts/backup.sh` (горячий `.backup` + `gzip` + `.sha256`, ротация 7 штук).
3. `git checkout main && git pull --ff-only origin main`.
4. `npm ci` — строго по `package-lock.json`; **не** `npm install` и **не** `npm audit fix` на проде: обновления зависимостей делаются в `dev`, проверяются там и приезжают через PR.
5. `APP_ENV=production npm run db:migrate` — миграции применяются **до** сборки: `next build` на этапе сбора данных страниц открывает базу и на старой схеме может упасть.
6. `npm run build` (в проде работает без ухищрений: Next сам подхватывает `.env.production.local`).
7. `sudo systemctl start qnabotai`.

**Проверка после запуска:** `systemctl is-active qnabotai`; логи старта (`journalctl -u qnabotai`) должны содержать `[server] database: …`, `[server] qdrant collection: …`, `[bot] started`, `[server] ready on …`; роуты: `/` и `/admin` → `307`, `/admin/login` → `200`, `/api/qna` без сессии → `401`; затем ручная проверка админки и бота.

**Проверка уязвимостей** (`npm audit`) — часть подготовки релиза, выполняется в `dev` перед PR, не на проде.

> `sudo` есть только у пользователя, поэтому шаги 1 и 7 — а значит и `scripts/deploy.sh` целиком — запускает пользователь, не агент.
