# Журнал решений (Decision Log)

Лёгкий ADR для solo-разработки. Здесь хранится **почему** сделано так, а не **как** (как — в `spec.md`).
Правило: записывать только архитектурные / доменные решения. Мелочи (стиль, нейминг переменных) сюда не пишем.

Формат записи:

```
## YYYY-MM-DD — Короткий заголовок
**Контекст:** что заставило решать.
**Решение:** что выбрали.
**Почему / альтернативы:** 1–2 строки.
```

> Записи ниже датированы приблизительно — они перенесены из `plan.md` задним числом на раннем этапе проекта.

---

## ~2026 — Анонимность бота (must-have)
**Контекст:** бот логировал Telegram `userId` для неотвеченных вопросов; планируется публичный режим.
**Решение:** `userId` нигде не сохраняется и не отображается (UI, экспорт, БД). Бот анонимный.
**Почему:** приватность пользователей; для FAQ-сценария идентификатор не нужен. Это жёсткий инвариант.

## ~2026 — Единая таблица `qna_items` вместо двух
**Контекст:** неотвеченные вопросы жили в отдельной таблице `unanswered_queries`, FAQ — в `qna_items`; в админке две вкладки.
**Решение:** удалить `unanswered_queries`, всё вести в `qna_items`. Неотвеченный вопрос = строка со `status="unanswered"` и пустым `answer`.
**Почему / альтернативы:** по факту это одна сущность в разных состояниях. Объединение в одну сущность с lifecycle проще, чем синхронизировать две таблицы. Историю прошлой таблицы (1 запись) не сохраняли.

## ~2026 — Lifecycle `unanswered → active → deleted`, статус `pending` удалён
**Контекст:** был статус `pending` (черновик до публикации), но upload фактически сразу создавал `active`.
**Решение:** единый lifecycle `unanswered → active → deleted`. Статус `pending` выпилен из схемы, фильтров, бэйджей. Удаление — soft-delete (`status="deleted"`).
**Почему / альтернативы:** `pending` не использовался по назначению и плодил путаницу. Soft-delete оставляет возможность восстановления из корзины (в backlog).

## ~2026 — Доменный термин `qna` (а не `faq`)
**Контекст:** после переименования проекта `faqbotai` → `QnABotAI` код использовал смешанный термин `faq`.
**Решение:** доменный идентификатор (таблица, коллекция Qdrant, роуты, UI-надписи) — `qna`. БД перезалита с нуля.
**Почему / альтернативы:** единообразие с именем проекта. Слово «FAQ» оставлено в естественном языке (README) как общеизвестный термин — переименовывать живой текст не нужно.

## ~2026 — Обработка дублей: подсвечивать, а не блокировать
**Контекст:** повторная загрузка FAQ создаёт дублирующие записи.
**Решение:** не запрещать дубли автоматически и не авто-обновлять записи, а подсвечивать возможные дубли и оставлять решение пользователю.
**Почему / альтернативы:** авто-блок и авто-обновление рискуют потерять/перетереть правильные данные молча; контроль за пользователем безопаснее на текущем этапе.

## ~2026 — Настройки RAG-пайплайна вне MVP
**Контекст:** обсуждались настройки чанкинга, эмбеддингов, параметров поиска.
**Решение:** это advanced-функциональность для технически подготовленных пользователей, в MVP не входит.
**Почему:** обычному преподавателю эти параметры не нужны; усложняют UI без пользы на текущем этапе.

## ~2026 — Бот не генерирует ответы («Судья», а не генератор)
**Контекст:** риск галлюцинаций LLM в ответах студентам.
**Решение:** LLM используется только как «Судья» — выбирает готовый ответ из топ-3 кандидатов Qdrant или возвращает `NULL`. Ответы только из базы знаний.
**Почему:** для учебного FAQ цена неверного ответа высока; статичные проверенные ответы надёжнее генерации.

## 2026-05-31 — «Не знаю» + human-in-loop предпочитаем достраиванию контекста
**Контекст:** на тесте ловушек бот вернул `NULL` на корректном вопросе («бот выключается через 10 сек на Vercel»), хотя нужный ответ был топ-1 в поиске (score 0.876). Причина: «Судья» видит только тексты вопросов кандидатов, а не их ответы, и формулировка «как починить» не совпала с «как задеплоить». Мост между ними («ограничены 10-15 сек») лежал в скрытом от «Судьи» ответе.
**Решение:** не «улучшать» этот случай (не ослаблять промпт «Судьи», не менять модель, не расширять его контекст). Ответ `unanswered` корректен: вопрос осядет в базе со `status="unanswered"`, преподаватель допишет ответ → пара станет `active`. Расширять контекст «Судьи» (например, отдавать ему и текст ответа) — только если практика покажет реальную потребность.
**Почему / альтернативы:** убрать «точно» из промпта → «Судья» начнёт хватать похожие-но-неверные ответы (ломает различение в ловушках с близкими парами). Модель поумнее не поможет — это пробел в знаниях, а не в рассуждении. Для учебного FAQ честное «не знаю» безопаснее уверенной чуши, а lifecycle `unanswered → active` уже закрывает этот сценарий без кода.
