# Журнал решений (Decision Log)

Лёгкий ADR для solo-разработки. Здесь хранится **почему** сделано так, а не **как** (как — в `spec.md`).
Правило: записывать только архитектурные / доменные решения. Мелочи (стиль, нейминг переменных) сюда не пишем.

Формат записи:

```
## YYYY-MM-DD — Короткий заголовок
**Контекст:** что заставило решать.
**Решение:** что выбрали.
**Почему / альтернативы:** 1–2 строки.
```

> Записи ниже датированы приблизительно — они перенесены из `plan.md` задним числом на раннем этапе проекта.

## 2026-08-08 — Эмбеддинги пачками через общую очередь; сбой индексации не отменяет загрузку

**Контекст:** транскрипт урока на 113 000 символов даёт 102 фрагмента, и каждый эмбеддился отдельным запросом. Лимит Mistral — 60 запросов в минуту (`x-ratelimit-limit-req-minute`), поэтому на ~61-м фрагменте прилетал 429, короткие ретраи (1/2/4 с) не переживали минутного окна, и исключение валило `processDocument` до извлечения пар. Преподаватель не получал ни черновиков, ни полного материала: на проде осталось 102 фрагмента в SQLite против 60 точек в Qdrant. Воспроизведено в dev на том же файле.

**Решение:** три уровня защиты. (1) `embedTexts()` шлёт до 32 текстов / 32 000 символов одним запросом — 102 запроса превратились в ~4. (2) Все вызовы эмбеддингов процесса идут через одну очередь с интервалом не быстрее 1 запроса в секунду, повторы после 429 — 5 / 15 / 45 с (сумма больше минутного окна) или по заголовку `Retry-After`. (3) Ошибка индексации больше не фатальна: пачки пишутся в Qdrant по мере готовности, `processDocument` возвращает `{ imported, chunks: { total, indexed } }`, черновики создаются всё равно, а админка предупреждает о неполном поиске. Поведение — в `spec.md` §3.2.

**Почему / альтернативы:** можно было ограничиться троттлингом, но тогда загрузка транскрипта растянулась бы на 102 секунды и упёрлась в таймаут прокси; пакетная отправка снимает проблему по существу, а очередь остаётся страховкой для файлов на тысячи фрагментов. Делать индексацию фатальной удобно для инварианта «SQLite и Qdrant совпадают», но цена — потеря всей работы LLM из-за временной ошибки инфраструктуры; расхождение честнее показать преподавателю и лечить `qdrant:reindex`.

## 2026-08-06 — Прод-клон изолирован от `dev` на уровне git, деплой оформлен скриптом

**Контекст:** через два часа после релиза прод-копию молча переключило с `main` на июльский `dev`; кто это сделал, установить не удалось (в bash history, cron и транскриптах агентов следов нет). Сервис это пережил — он отдаёт готовую сборку из `.next`, а код бота уже был в памяти, — но перезапуск в тот момент поднял бы бота на июльском коде против мигрированной базы. Тогда же выяснилось, что сам деплой выполнялся из dev-окна через `cd` в прод-папку и что `npm run db:migrate` без `APP_ENV` отмигрировал в прод-папке dev-базу (`data/logs-dev.db`).

**Решение:** граница между двумя рабочими папками перенесена из головы в инструменты. В прод-клоне удалена ветка `dev` и сужен `remote.origin.fetch` до одной `main`, так что `git checkout dev` там невозможен; вторым рубежом — хук `post-checkout` с версионируемым источником `scripts/prod-post-checkout.sh`. Деплой оформлен как `scripts/deploy.sh` с проверками «это прод-клон», «ветка `main`», «дерево чистое» и явным `APP_ENV=production`. Детали — `spec.md` §7.4.

**Почему / альтернативы:** одной дисциплины «работаю в dev, деплою в проде» не хватает — ошибка того же класса воспроизвелась в тот же вечер. Удалить локальную ветку без сужения refspec недостаточно: git молча пересоздаёт её из `origin/dev`. Запретить агентам ходить в чужую папку одними правилами тоже нельзя — правила не исполняются механически, поэтому проверки живут внутри скрипта.

## 2026-08-06 — Деплой через ветку `main`, сервис останавливается до `git pull`

**Контекст:** раньше прод стоял на `dev` и обновлялся прямо из неё, то есть на бою мог оказаться любой промежуточный коммит. Плюс 2026-08-05 деплой пришлось ставить на паузу и откатывать прод-папку на старый коммит именно потому, что новый код уже лежал на диске, а миграции ещё не применились.

**Решение:** прод живёт на `main`, код туда попадает только через PR `dev → main` merge-коммитом. Сервис останавливается **до** `git pull` и поднимается только после миграций и сборки. Миграции — до `npm run build`, зависимости на проде — только `npm ci`. Полный порядок и проверки после запуска — `spec.md` §7.4.

**Почему / альтернативы:** деплой прямо из `dev` не даёт точки «что сейчас на проде» и требует дисциплины «не пушить в dev ничего сырого». Обновление без остановки сервиса короче на пару минут простоя, но оставляет окно, в котором автоперезапуск юнита поднимет новый код на старой схеме БД — на этом уже спотыкались. Для пилота, где нагрузки почти нет, простой дешевле риска.

## 2026-08-06 — `Docs/plan.md` остаётся в git; коммитим только в двух точках

**Контекст:** во время работы по шагам плана файл постоянно меняется, и его коммиты либо шумят в истории, либо подмешиваются в фичевые. Возник вопрос, не проще ли внести `plan.md` в `.gitignore`.

**Решение:** файл остаётся отслеживаемым. Во время работы по шагам не коммитим. Коммитим отдельным `docs(plan): ...` в двух случаях: (1) заход закрыт — итоги перенесены в `decisions.md`/`spec.md`, план очищен; (2) заход встаёт на длительную паузу — тогда коммитим план с галочками и остатком, чтобы контекст «на чём остановились» не жил на одной машине.

**Почему / альтернативы:** `.gitignore` + `git rm --cached` обрывает накопленную историю планов, убирает файл из свежих клонов и расходится с правилом в `CLAUDE.md`, где `plan.md` назван каноническим артефактом плана. Коммит в конце захода даёт тот же результат по шуму, но сохраняет историю.

## 2026-08-01 — Генерация черновиков ответов: RAG по лекциям + отсылка к минуте видео

**Контекст:** последний пункт P1.85 — «Сгенерировать ответ» для вопросов без ответа. Заказчик подтвердил (переписка 2026-07-31): ответ собирать из его лекций, а не из общих знаний LLM, и указывать, в каком уроке на какой минуте это рассказывается.

**Решение:** хранить материалы: таблицы `documents` + `doc_chunks` (фрагменты ~1000 символов; для SRT/VTT — секунда начала из таймкодов, которые раньше выбрасывались); эмбеддинги фрагментов — в отдельную коллекцию `{QDRANT_COLLECTION}_docs`. `POST /api/qna/[id]/generate`: топ-4 фрагмента → `mistral-small-latest` собирает ответ строго по ним (JSON `{answer, source}`, `null` = честный отказ) → к черновику добавляется «Подробнее: <файл>, ~N-я минута». Повторная загрузка файла с тем же именем заменяет документ. Генерация только в админке; ученикам уходит одобренный текст.

**Почему / альтернативы:** генерация «из головы» LLM проще (без хранения), но расходится с подачей курса и не даёт отсылку к уроку — заказчик явно попросил «по материалу с таймстемпом». Смешивать фрагменты с парами в одной коллекции Qdrant — грязный поиск для «Судьи»; отдельная коллекция дешевле фильтров по payload.

## 2026-07-28 — Модерация LLM-извлечённых пар: статус `draft`, доверенные пути без модерации

**Контекст:** пары, извлечённые ИИ из документов, попадали в базу знаний сразу как `active`; заказчик хочет проверять их перед публикацией (P1.85).

**Решение:** новый начальный статус `draft` в lifecycle (`unanswered | not_helpful | draft → active → deleted`); в него попадают только пары из «Загрузить документ» (LLM-экстракция), без индексации в Qdrant до одобрения. Excel и ручной ввод остаются сразу `active` — там пары готовит сам преподаватель. Вкладка «Черновики» + массовая публикация выбранного (`POST /api/qna/bulk-publish`).

**Почему / альтернативы:** экран предпросмотра до записи в БД — потеря черновиков при закрытии вкладки и отдельный UI; модерация всех путей подряд — лишний клик там, где преподаватель и так автор. Статус в общей таблице переиспользует готовый механизм публикации.

## 2026-07-23 — «Не помогло» — отдельный статус со снапшотом отвергнутого ответа

**Контекст:** вопрос, на который бот не нашёл ответа, и вопрос с отвергнутым учеником ответом требовали разных действий преподавателя, но оба попадали в `unanswered`.

**Решение:** добавить начальный статус `not_helpful` в lifecycle (`unanswered | not_helpful → active → deleted`) и поле `qna_items.rejected_answer`. В админке — отдельный фильтр/бейдж «Не помогло» и показ отвергнутого ответа рядом с полем для исправленного ответа.

**Почему / альтернативы:** отдельная таблица обратной связи дублировала бы редактируемую очередь `qna_items`; одного вердикта в read-only журнале недостаточно для рабочего списка преподавателя. Пользовательское название совпадает с кнопкой ученика и не требует объяснений.

## 2026-07-15 — TXT/SRT/VTT через существующий LLM-путь, субтитры чистим сами

**Контекст:** заказчик не смог загрузить транскрипты уроков — принимались только PDF/DOCX/XLSX; транскрипты у него в TXT и субтитрах SRT/VTT.

**Решение:** расширить путь B: TXT читается как есть, SRT/VTT очищаются от таймкодов/номеров/тегов регэкспами (`subtitlesToPlainText`) без новых зависимостей; дальше та же LLM-экстракция пар. Для текстовых типов расширение файла приоритетнее MIME браузера; вместо magic bytes — проверка «валидный UTF-8 без NUL-байтов» (+ `WEBVTT` для .vtt).

**Почему / альтернативы:** библиотека парсинга субтитров — лишняя зависимость ради тривиального формата; отдельный пайплайн для транскриптов не нужен — существующий путь B ровно для этого.

## 2026-07-15 — Две рабочие папки на сервере + guard окружений в `validateEnv`

**Контекст:** дев и прод на одной машине; дев запускался из прод-папки (`next dev` затирает прод-сборку в `.next/`), а общий Qdrant делает опечатку в `.env` тихой катастрофой (dev-векторы в прод-коллекции).

**Почему / альтернативы:** второй Qdrant-контейнер — лишние ресурсы при том же уровне риска; два GitHub-репозитория — ручная синхронизация кода. Изоляция данных именами + fail-fast проверка дешевле и достаточна для пилота.

## 2026-07-07 — Разделение SQLite по окружениям (`DATABASE_PATH`)

**Контекст:** шаг 0.1 плана prod — dev и prod на одном VPS, но общая `logs.db` создавала риск испортить production из dev (reindex, миграция, тестовые данные).

**Решение:**
- Единственный путь к БД — обязательная переменная **`DATABASE_PATH`** в `.env.{env}.local` (`data/logs-dev.db`, `data/logs-staging.db`, `data/logs-prod.db`).
- `src/db/index.ts`: `new Database(DATABASE_PATH)`, `mkdir -p` для каталога; `preload-env.ts` вызывает `validateEnv()` до импорта `@/db`.
- `drizzle.config.ts` и `npm run db:migrate` используют тот же `loadEnv()` + `DATABASE_PATH`.
- `scripts/backup.sh` — только prod: читает `DATABASE_PATH` из `.env.production.local`, архив `backups/logs-prod-<дата>.db.gz` + sha256.
- Одноразовая миграция: `logs.db` → `data/logs-prod.db`, старый файл → `logs.db.legacy` (не удалять сразу).

**Почему / альтернативы:** ветвление по `APP_ENV` в коде хуже, чем явный путь в env — проще staging и перенос на отдельный сервер. Qdrant-коллекции — отдельный шаг 0.2.

## 2026-07-05 — Cursor / AI tooling boundaries

**Контекст:** P1.5 — перед prod нужно явно ограничить, какие данные попадают в Cursor и внешние LLM при разработке с AI-ассистентом.

**Решение:**
- **`.cursorignore`** (корень репозитория) — файлы из списка не индексируются и не попадают в контекст Agent/Chat автоматически: `.env`, `.env.*`, ключи (`*.pem`, `*.key`, …), `.ssh/`, `*.db`, `*.db.gz`, `qdrant_storage/`, `backups/`, `uploads/`, `node_modules/`, `.next/`, логи.
- **Privacy Mode в Cursor** — включить вручную: `Ctrl+Shift+J` (Linux/Windows) или `Cmd+Shift+J` (Mac) → **General** → **Privacy Mode** → **On**. Код не используется для обучения моделей Cursor и провайдеров; проверка — тот же экран настроек или [cursor.com/settings](https://cursor.com/settings). Privacy Mode не отменяет отправку контекста в модель на время запроса — только запрет на хранение и обучение.
- **Что AI видит:** исходный код из репозитория (кроме `.cursorignore`), `Docs/`, шаблоны `*.example`, открытые вручную файлы (в т.ч. игнорируемые — если явно прикрепить или открыть).
- **Что AI не видит автоматически:** секреты (`.env.*.local`), БД и бэкапы (`logs.db`, `backups/*.db.gz`), векторное хранилище, загрузки преподавателя.
- **Правила для разработчика:** не вставлять в чат значения из `.env.*.local`; не просить AI читать prod-секреты и дампы БД; prod-пароль админки — только через `npm run admin:hash-password`, не через чат.

**Почему / альтернативы:** `.gitignore` защищает git, но Cursor индексирует workspace отдельно — нужен `.cursorignore`. Privacy Mode — дополнительный слой на уровне аккаунта; для solo-пилота достаточно personal-настройки без team enforcement.

## 2026-07-05 — Trust boundaries (пилот)

**Контекст:** P1.5 — границы доверия реализованы в коде, но не были зафиксированы отдельно.

## 2026-07-05 — Backup-стратегия: бэкапим только SQLite, Qdrant переиндексируется

**Контекст:** P1.5 пункт 5.2 — перед публичным запуском нужна backup-стратегия. Данные живут в двух местах: `logs.db` (SQLite) и `qdrant_storage/` (векторный индекс). Уточнение контекста от пользователя: dev и prod — **один и тот же сервер**, отдельного прод-сервера нет и пока не планируется.

**Решение:**
- Источник правды — только `logs.db`; бэкапится только он: `scripts/backup.sh` (горячий `sqlite3 .backup` → `backups/logs-<дата>.db.gz`, ротация 7 шт.) + cron ежедневно в 03:00 UTC.
- Qdrant не бэкапится: написан `scripts/reindex.ts` (`npm run qdrant:reindex`), который пересоздаёт коллекцию `qna` из активных `qna_items` (проверено на 106 записях).
- Секреты (`.env.*.local`) в архивы не попадают — копия хранится вручную (менеджер паролей).
- Off-site копия (холодное хранилище Timeweb) — отложена в backlog P1.5: пока архивы только на диске сервера.

**Почему / альтернативы:** бэкапить `qdrant_storage/` — значит тащить производные данные и решать проблему консистентности двух бэкапов; переиндексация из одного источника правды проще и надёжнее. Цена — повторный расчёт эмбеддингов через Mistral при восстановлении (для пилота: ~полминуты и копейки). Порядок восстановления — `spec.md` §7.3.

## 2026-07-05 — Rate limiting: in-memory, без хранения chat_id

**Контекст:** P1.5 пункт 4 — перед публичным запуском нужны защита бота от спама, защита логина админки от перебора пароля и видимость сбоев бота. Лимит «на пользователя» требует какого-то идентификатора чата, а инвариант анонимности запрещает сохранять Telegram ID в БД.

**Решение:**
- Все счётчики — только в памяти процесса (`src/lib/rate-limit.ts`), в БД ничего не пишется: `chat_id` бота и IP админки живут в `Map` с TTL/скользящим окном и исчезают при рестарте. Инвариант анонимности не нарушен.
- Бот: 3 вопроса в минуту на чат, проверка в начале `message:text` — до Qdrant/Mistral (заблокированные запросы не тратят токены). Уведомление о лимите — один раз за эпизод блокировки, дальше молчание (иначе сам ответ бота становится каналом спама).
- Логин: считаются только неудачные попытки — 5 с одного IP → 429 на 15 минут, успешный вход сбрасывает счётчик.
- Аудит: в `bot_log` добавлен вердикт `error` + колонка `error` (текст ошибки без stack trace); catch-блок бота пишет запись best-effort.

**Почему / альтернативы:** Redis/persist-хранилище для лимитов — избыточно для пилота на одном сервере; сброс счётчиков при рестарте приемлем. Хранение hash(chat_id) в БД рассматривалось и отклонено: для целей лимита персистентность не нужна, а инвариант чище держать без исключений.

## 2026-07-04 — Аудит секретов: убрать fallback в базовом `.env`

**Контекст:** код-ревью реализации из решения выше. Базовый `.env` (грузится первым для любого `APP_ENV`) продолжал хранить полный набор секретов dev-окружения (токен бота, ключи Mistral/OpenRouter, хеш пароля, `SESSION_SECRET`) — то есть дублировал `.env.development.local`. Симуляцией подтверждено: если запустить `npm start` (`APP_ENV=production`) без `.env.production.local`, `validateEnv()` не заметил бы проблему — все переменные казались бы заданными, но фактически со значениями dev-бота. Бот ушёл бы в «прод» под видом продакшена, но с dev-токеном.

**Решение:** `.env` очищен до общих несекретных значений (`QDRANT_HOST`, `QDRANT_PORT`). Все секреты — только в `.env.{env}.local`. Проверено: `npm run dev:server` работает как прежде; симуляция запуска с `APP_ENV=production` без `.env.production.local` теперь корректно падает с понятной ошибкой из `validateEnv()`.

**Почему:** базовый `.env` как «общий слой для всех сред» — это анти-паттерн, если в него положить хоть один секрет: он становится тихим источником значений по умолчанию для окружений, где явный секрет ещё не задан. Единственный безопасный контент базового `.env` — не-секретные значения, одинаковые для всех сред.

**Статус прод-бота (2026-07-04, обновлено):** после аудита пользователь сначала предложил использовать существующий бот как «прод», но по факту это уже боевой бот, которым пользуются dev-сессии — решили не трогать («оставим его в покое») и завести для production отдельного бота: `@VibeCodingFAQBot` (проект — онлайн-академия VibeCoding). Токен получен, добавлен в `.env.production.local`. `MISTRAL_API_KEY` для прода переиспользован из dev — это ключ доступа к API, не привязан к идентичности бота, шарить между окружениями для соло-пилота приемлемо. Пароль админки и `SESSION_SECRET` для прода — отдельные, не как в dev. Пункт 2 закрыт; реальный деплой (сам prod-сервер) — предстоит позже, `.env.production.local` подготовлен заранее.

## 2026-07-03 — Авторизация админки: пароль без логина, вечная сессия

**Контекст:** `/admin/*` был открыт всем без аутентификации (P1.5, пункт 1). Пилот на одного преподавателя — полноценная multi-teacher инфраструктура не нужна (см. P2 в `backlog.md`).

**Решение:**
- Один пароль без логина (админ единственный), bcrypt-хеш хранится в `.env` в виде **base64** (`ADMIN_PASSWORD_HASH_BASE64`), проверяется в `POST /api/auth/login`.
- Сессия — подписанный HMAC-SHA256 cookie-токен (`SESSION_SECRET` в `.env`), без хранения сессий на сервере/в БД. Срок жизни — 1 год (по факту «вечная» сессия до logout или очистки cookie).
- Защита реализована через Next.js proxy (`src/proxy.ts`, начиная с Next.js 16 — переименованный `middleware.ts`): редирект на `/admin/login` для страниц и `401` для API (`/admin/*`, `/api/qna/*`, `/api/log/*`).
- Пароль задаётся через CLI-скрипт `npm run admin:hash-password -- "пароль"`, который печатает base64-строку для `.env`.

**Побочная находка:** обычный bcrypt-хеш (`$2b$10$...`) хранить в `.env` напрямую нельзя — Next.js при загрузке `.env` интерпретирует `$2b`, `$10` и т.д. как ссылки на другие переменные окружения и молча портит значение (переменная теряет начало хеша). Base64-обёртка полностью убирает `$` из значения и решает проблему.

**Почему / альтернативы:** для одного админа полноценная auth-инфраструктура (users-таблица, OAuth, refresh-токены) избыточна. Подписанный cookie без серверного хранилища сессий — самый простой обратимый вариант, которого достаточно для пилота. Multi-teacher логин (логин = Telegram username, пароли выдаёт владелец) отложен в P2.

**Контекст:** был статус `pending` (черновик до публикации), но upload фактически сразу создавал `active`.

**Почему / альтернативы:** `pending` не использовался по назначению и плодил путаницу. Soft-delete оставляет возможность восстановления из корзины (в backlog).

## 2026-07-02 — Журнал обращений к боту: новая таблица `bot_log`, кандидаты — JSON-поле
**Контекст:** сейчас фиксируются только неотвеченные вопросы (`qna_items.status="unanswered"`); успешные ответы бота нигде не логируются, и нет возможности проверить, что «Судья» выбирает правильные ответы. Нужен журнал для наблюдаемости — фундамент для будущей debug-панели (P2).

## 2026-05-31 — «Не знаю» + human-in-loop предпочитаем достраиванию контекста
**Контекст:** на тесте ловушек бот вернул `NULL` на корректном вопросе («бот выключается через 10 сек на Vercel»), хотя нужный ответ был топ-1 в поиске (score 0.876). Причина: «Судья» видит только тексты вопросов кандидатов, а не их ответы, и формулировка «как починить» не совпала с «как задеплоить». Мост между ними («ограничены 10-15 сек») лежал в скрытом от «Судьи» ответе.
**Решение:** не «улучшать» этот случай (не ослаблять промпт «Судьи», не менять модель, не расширять его контекст). Ответ `unanswered` корректен: вопрос осядет в базе со `status="unanswered"`, преподаватель допишет ответ → пара станет `active`. Расширять контекст «Судьи» (например, отдавать ему и текст ответа) — только если практика покажет реальную потребность.
**Почему / альтернативы:** убрать «точно» из промпта → «Судья» начнёт хватать похожие-но-неверные ответы (ломает различение в ловушках с близкими парами). Модель поумнее не поможет — это пробел в знаниях, а не в рассуждении. Для учебного FAQ честное «не знаю» безопаснее уверенной чуши, а lifecycle `unanswered → active` уже закрывает этот сценарий без кода.
